# 10. 存储生命周期与性能怎样一起考虑

[教学手册目录](index.md) · 返回：[Encaps 完整示例](06-encaps-walkthrough.md)

硬件优化经常是在“保留数据、重算数据、搬运数据”之间取舍。先画对象的最后一次读取，再谈省 SRAM；先统计资源等待，再谈增加计算 lane。

## Encaps 的页生命周期

| 页 | 内容 | 首次生成 | 最后使用 / 可以覆盖的时机 |
|---|---|---|---|
| 0..2 | t_hat | 公钥解码 | v 点积结束 |
| 4..6 | y_hat，秘密 | y 采样和 NTT | 所有 u 行及 v 点积结束；随后按安全策略清理 |
| 8 | 当前累加器 | 每行开始清零 | 本行压缩完成；下一行重新清零 |
| 9 | e1/e2，随后压缩系数 | 当前行采样 | 加噪声结束才允许压缩结果覆盖；pack 结束才允许下轮采样覆盖 |
| 10 | 一个矩阵元素 | 当前 (row,col) 采样 | 对应乘累加完成，才能生成下一个元素 |
| 11 | 公钥解包暂存 / 密文打包暂存 | COPY 或 PACK | 对应 UNPACK 或 COPY_OUT 已消费完毕 |
| 16..17 | 编码公钥 | DMA 搬入 | 公钥哈希及解码所需读取全部完成 |
| 20..21 | 编码密文 | 每行 COPY_OUT | 顶层输出流程完成后才能回收 |
| 22 | K，秘密 | SS 状态 | 输出消费并完成必要的秘密清理 |

此表描述逻辑依赖，不声称 RTL 已实现动态回收器。页可复用也不表示旧秘密已经物理擦除；权限、有效位、擦除是不同动作。取消时还要处理在途读者，见[时序章节](08-timing-waveforms.md)。

如果存完整的 3×3 矩阵，仅矩阵就要 9 个展开页。当前方法只留一个元素页，节省 8 KiB，却让采样与乘累加沿串行依赖推进。缓存矩阵或双缓冲可能增加重叠机会，但要付出额外 SRAM、端口和控制复杂度。

## Bank 冲突不是算法错误

如果两个同拍访问落在同一个单端口 bank，就必须仲裁或改排程。Python 模型的简单 `%banks` 映射适合观察冲突；HLD 的 XOR bank 映射另有设计，二者的冲突统计不能直接互换。当前 SRAM RTL 又是带仲裁和 ECC 的寄存器数组实现，不能据此推算最终 macro 的 PPA。

教学例子使用 word_address%8：地址 0 与 8 冲突，0 与 1 不冲突。改变 bank 数、端口数或映射都会改变结果。“两个 lane”并不保证每拍两个蝶形，因为每个蝶形还需要读取、乘法、写回和正确的数据依赖。

## 给周期数字加上口径

KEM 前向 NTT 有 7 层，每层 128 个蝶形，合计 896 个。忽略存储及启动成本，2 lane 的理想工作量是 448 拍。Encaps-768 对 y 做 3 次前向变换，对 3 行 u 和 v 做 4 次逆变换；每个逆变换也有对应的 7 层，但最终归一化、流水和访存要另外计入。不能把 `7×448` 直接称为完整 Encaps 延迟。

| 开销 | 怎样观察 | 常见误判 |
|---|---|---|
| 哈希吸收、置换、挤出 | 输入/输出握手计数及 hash_done | 用纯 Keccak 轮数代替整次 hash 延迟 |
| 矩阵生成 | 9 次 XOF 请求、采样完成与排空时间 | sampler_done 后就停止计时 |
| 多项式运算 | 每种 op 的 start 到 done | 用理想蝶形数忽略 SRAM 等待 |
| Codec | 逐系数读取与字节打包 | 认为压缩只是接线 |
| 搬运 | AXI 所有通道及写响应 | 带宽峰值就是命令吞吐量 |
| 清理与提交 | zeroize、输出响应、completion | 算法 done 就是对软件完成 |

当前 Encaps 每个矩阵元素请求 4096 B SHAKE 输出，9 个元素共 36864 B。这个量可能显著影响实际延迟，即使取够系数平均只需要其中一部分。优化前必须保持拒绝采样正确性、失败处理和安全约束，不能仅把上限随意缩小。

仅考虑对外有效载荷，公钥输入 1184 B，加输出密文 1088 B 和 K 32 B，共 2304 B。若理想化每拍单向合计搬 16 B，需 144 个有效数据拍；这还没算描述符、completion、地址通道、响应、突发边界和背压，也没利用真实系统可能存在的读写并行。它是一个教学计数口径，不是完整命令的严格延迟预测。

## 一个可以复现的性能实验

运行[bridge_demo.py](../examples/bridge_demo.py)，看尺寸、理想蝶形计数和简单 bank 冲突；再在仿真中分别统计：总命令周期、hash 等待、SRAM 等待、输出响应等待。若阶段串行，可以相加；若有重叠，必须看时间区间的并集，不能把重叠部分重复计费。

检查题：把 lane 从 2 改成 4，完整 Encaps 一定快两倍吗？不一定。若主要耗时在 SHAKE 排空或存储等待，多项式算术加倍只改善其中一部分。进一步阅读[硬件流程与目标性能](03-flows-memory.md)，始终区分目标、理想计数、仿真和物理测量。

# 5 · 怎样阅读 RTL 与验证结果

[上一章](04-security-errors.md) · [教学手册首页](index.md)

## 5.1 先建立一条可追踪的证据链

```text
算法要求 → 数据表示/接口 → 状态机与 RTL → 输入向量 → 检查器 → 日志/结果
```

如果中间缺一环，“通过”可能只说明某个工具正常结束。学习本项目时，应先问测试比较了什么，再问通过了多少个。

| 测试类型 | 能支持的结论 | 不足以支持的结论 |
|---|---|---|
| Python 算法互操作 | 两实现对外结果兼容 | 自研 RTL 完整正确 |
| NTT 往返 | forward/inverse 互逆 | 标准变换域乘法及中间排列正确 |
| 原语 UT | 某个模块在所测条件下符合期望 | 全算法及顶层完成链正确 |
| 顶层 KAT | 固定输入的真实硬件输出符合期望 | 所有负向、配置和时序场景覆盖 |
| runner 故障注入 | 测试工具能识别伪成功等错误 | DUT 算法通过 |
| lint / 结构门禁 | 某类静态规则与材料结构符合要求 | 侧信道安全、STA、CDC 或可发布 |

## 5.3 推荐的 RTL 阅读顺序

1. 从 `pqc_pkg.sv` 看 opcode、参数集、状态和运算模式。
2. 从 `pqc_top.sv` 找一个明确操作的 start、输入 mux、done 与 completion 路径。
3. 进入该专用程序，先画状态分组：取数、启动、等待、保存、推进、失败。
4. 选一个引擎，追踪输入配置何时锁存，done 对应哪次请求。
5. 跟踪 SRAM 请求的地址单位、返回归属、读写优先级和 clear 条件。
6. 打开对应测试，检查是否比较完整字节、背压、取消和连续命令。

不要按文件长度从头读到尾。先回答一条具体问题，例如“Decaps 的原始 c 会在 J 计算前被覆盖吗”，再沿相关信号寻找证据。

## 5.4 模型与 RTL 如何对照

指定的 Python 完整 API 调用外部算法库，自研底层模型独立。要与 RTL 比较中间值，需要选择并冻结 checkpoint：输入 bytes、采样结果、每个 NTT stage、乘加输出、编码前系数、最终输出。

一个好的 checkpoint 至少记录参数集、域表示、数组排列、字节/word 单位、逻辑对象和数据长度。数值不同先核对这些条件，再判断算法错误。

最终标准格式可以直接逐字节比较；中间 NTT 数组可能因为排列或 Montgomery 因子不同而不宜直接比较，需要先转换到相同定义。模型自身可逆不能解决这种对齐问题。

## 5.6 三个小项目练习

**练习 A：解读一个状态机。** 选择 `pqc_key_custody`，画出 HEADER 到 ACK 的状态图；标注每步何时消耗一个 word，为什么错误身份 ACK 不允许推进。

**练习 B：跟踪一次背压。** 在纸上列出 6 个时钟，令 ready 序列为 1、0、0、1、1、1；画出 valid、data、index。只有握手沿才推进，阻塞期间数据不变。

**练习 C：区分三层通过。** 分别找出一个 Python 算法测试、一个原语 UT、一个顶层 KAT，写一句话说明各自输入、比较对象及尚未覆盖的部分。

完成后，你应当能用数据依赖、身份和证据解释硬件行为，而不仅是复述模块名称。
